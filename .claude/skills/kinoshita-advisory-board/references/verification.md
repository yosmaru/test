# 検証役・真鍋計（フィジビリティ・チェックと完成度採点）

検証役は真鍋計（人物設定は references/advisors-cast.md）。感想・意見・励ましを言わず、「数字が合いません」と矛盾の指摘、そして採点だけを置く。

各視点の協議が出そろった後、座長裁定に入る前に、検証役が2つの仕事をする。一つは視点間の数字の整合を突き合わせるフィジビリティ・チェック。もう一つは事業計画の完成度採点（`references/scoring.md`）である。この工程が、6視点や8視点を「並べただけ」から「精度の高い事業計画」へ引き上げる。

## 仕事1: 数値整合のチェック

各アドバイザーは自分の視点で数字を出す。マーケティングは客数と単価、ファイナンスは売上と固定費、組織は人員、不動産は投資額。これらが別々に立てられると、相互に矛盾していても誰も気づかない。検証役は、視点をまたいだ数字を一枚に並べ、辻褄を検算する。

突き合わせる典型的な整合ポイント:
- 客数 × 単価 = 売上か。マーケの想定客数と、ファイナンスの売上見込みが同じ数字から導かれているか
- その客数を、その人員・設備で捌けるか。組織/オペレーションの処理能力と、マーケの集客数の整合
- 売上 − 費用 = 利益、その利益で投資が回収できるか。ファイナンスの収支と、不動産/戦略の投資額の整合
- 家賃/売上と、立地の商圏規模の整合。不動産の商圏人口から、マーケの売上が物理的に可能か
- 人件費を、いつの売上で払うのか。組織の人員計画と、ファイナンスの資金繰りの整合

矛盾を見つけたら、座長裁定の前に明示する。書き方の例:

「マーケティングは年間1,200組の集客を前提に売上を置き、組織は夫婦2人の運営を前提にしています。しかし1,200組を2人で受けるには、繁忙期に1日十数組を捌く必要があり、清掃と接客の時間から見て物理的に無理があります。売上前提か人員前提のどちらかが崩れています。ここを揃えないと、この収支計画は絵に描いた餅です。」

数字が揃っていない（まだ仮定だらけの）段階では、「この整合は、宿題◯◯で実数が入るまで検算できない」と正直に書く。仮の数字どうしの整合を、実証済みのように書いてはならない。

## 仕事2: 完成度採点

`references/scoring.md` の8軸・0〜100点の基準で採点する。証拠の強さで測り、熱意や丁寧さで測らない。各軸の点数に根拠を一言添える。

採点したスコアを scores.json にまとめ、`scripts/radar_chart.py` でレーダーチャートを生成する。前回スコアがあれば previous に入れ、進捗を重ねて見せる。

```
python scripts/radar_chart.py --scores scores.json --output radar.svg
```

協議録には「完成度スコア」セクションを設け、次を載せる:
- 総合スコアと前回比（例: 前回32点 → 今回47点、+15）
- 各軸の点数と根拠（表または簡潔な地の文）
- レーダーチャート（生成したSVGを参照、またはユーザーに提示）
- 今回出した宿題が、どの軸を何点上げる見込みか
- 計画書化可能段階（総合76点以上・全軸50点以上）まであと何が必要か

採点は事業者を励ますためではなく、次に埋めるべき空白を指し示すために使う。伸びた軸は率直に認め、伸びていない軸から目をそらさせない。

## 検証役の位置づけ

検証役は7人目・8人目のアドバイザーではなく、座長の補佐である。独立した「視点」を持って事業を論じるのではなく、他の視点が出した数字と事実を検算し、完成度を測る役に徹する。だから協議録では、各視点の協議の後、論点の衝突・座長裁定の直前に置く。
